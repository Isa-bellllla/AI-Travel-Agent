# 通用对话与推荐逻辑（Update 3）

这是 Agent 层的流程改进：解释提示、状态更新、澄清决策、查询、排序、证据和呈现。没有微调底层 LLM 或改变其模型权重，也没有按示例句子编写专用检索分支。测试中的具体句子是回归输入，不是应用运行时的问答表。

## 一次用户输入的处理

1. LLM 结合当前输入与完整会话状态判断任务：推荐、事实查询、比较/计算、澄清、能力外请求，或用户表达结束意愿。
2. 把表达映射为结构化需求：国家、城市、品牌、数据库等级、预算，以及自由语义偏好。保存硬/软、肯定/否定、优先级、置信/待确认状态与来源轮次。新值替换旧值，但保留其他不冲突需求。
3. 对影响结果的重要歧义先提问。不理解的核心概念不能擅自解释为熟悉的设施；尚未确认的解释也不能当作已确认需求。低预算不转换成虚构金额；未提供地点时可询问地点，用户明确邀请探索时允许跳过。
4. 用只读工具先执行硬过滤，再做词汇与语义检索，并检查记录中的实际证据。主键仅负责酒店身份和追问引用，不是匹配用户意思的工具。源 CSV 无 hotel_id，应用以稳定派生 ID 定位记录。
5. 计算已提取语义偏好的加权证据覆盖率，并结合既有检索顺序排序。硬约束不得违反；相似度不是设施证据。没有支持任何语义偏好的记录时先说明未验证匹配、询问重要条件或是否放宽，不随机补足三个。匹配覆盖率只用于开发诊断，不是 rubric 的“识别出用户全部偏好概念”得分或准确率。
6. 返回面向用户的推荐理由、价格、匹配点和限制；事实问题直接回答对应字段或计算，不要求用户完成酒店搜索问卷。每次推荐后仍接受修改、比较和继续提问。

类别/品牌/地理位置使用实际来源字段与取值。标签或描述没有字面同词不一定表示不匹配：同义或改写表达应由 LLM 语义解释与记录证据建立联系。例如海边、靠海、beachfront 可以有关联，但酒店处于沿海城市本身不能证明酒店就在沙滩上。没有距离字段时不能虚构“步行五分钟”。

## 三种情况不能混在一起

- **用户意思不清楚**：问一个有针对性的问题，以理解用户想要的体验。
- **意思清楚但库里没有记录**：如实说未知或无法验证；不要反复要求用户重新定义一个已经明确的词。
- **理解且能查询，但硬条件没有符合结果**：说明未找到符合条件的记录，问是否愿意放宽某项条件；不要默默返回违背条件的酒店。

这不是逐词查字典。不影响结果的措辞无需澄清；用户可以跳过问题；也不必每次都补齐所有字段。

## 结束由用户控制

没有输入时应用不会自行生成消息，也不会因为输出一组推荐或达到若干轮就主动关闭对话。LLM 只有在当前消息表达感谢、满意或结束且没有剩余请求时才选择 close。该状态仅暂停，不清空偏好、酒店列表或历史。后续再提问会恢复 active。感谢后带着新问题的消息不能仅因包含感谢就结束。

New Conversation 由用户主动清空会话。普通会话存储在 Streamlit 会话内存中，不保证跨服务器重启/浏览器会话丢失后恢复；本改进没有增加持久化账户系统。

## 验证边界

记录运行中 58 个自动测试通过。除具体回归外，还检查了全部数据集城市的国家关系、全部国家的旧城市清理、全部已记录等级之间的互斥替换，以及品牌跨轮、未理解概念、暂定解释、零语义证据、结束后再继续等通用不变量。

这些测试使用可控的结构化计划来检验组件契约，不证明真实 LLM 会正确提取所有未见表达。当前云工作区没有用户的本地 API 凭据，未调用其实际模型。模型的语义理解、证据蕴含判断、真实澄清质量和 held-out rubric 分数仍需在用户环境中运行和审核。置信度阈值是保守决策门槛，不是校准过的正确概率。
