Travel AI Agent
Performance Evaluation Rubric  |  Version 1.0
System: Hotel recommendation agent using LLM + embeddings + retrieval-augmented generation (RAG)
Ground truth: cleaned_hotels.csv and an evaluator-approved test-case annotation sheet. All examples below are hypothetical; they are not verified hotel records.
1. Purpose and scoring policy
Assess (A) factual grounding, (B) preference recognition and recommendation relevance, and (C) intent understanding. Each criterion receives 0 or 1 point when applicable. An N/A designation is permitted only under the stage rules below. Response latency is reported separately and never changes the 0–3 quality score.

2. A — Factual accuracy (1 point)
Scope: Verify hotel names/IDs, city/country, brand level, labels, benefits, amenities, prices, seasonality, and any other factual property against the corresponding database row. A statement that a record does not establish a property is acceptable; silence on missing information is acceptable unless it creates a misleading impression.
PASS (1): Every hotel recommended is a real dataset record and every factual hotel claim is supported by that record. If a price was imputed, identify it as an estimate; do not claim live availability.
FAIL (0): Any non-dataset hotel, wrong hotel attribute, invented amenity, unverified availability, or estimated price presented as confirmed.
A clarification-only response with no hotel-specific claims passes factual accuracy if it makes no unsupported factual claims; do not invent a hotel merely to earn a score.
Evaluator method: Match hotel_id first (or validated unique key). Extract claims from the response, compare with the row, and record the exact unsupported claim and source field.
3. B — Preference recognition and recommendation relevance (1 point)
Before running each case, annotate expected explicit preference concepts (e.g., Abu Dhabi, luxury, family trip, ocean view, budget). Treat synonyms as equivalent. Do not count speculative preferences as correctly extracted. Define hard versus soft constraints in the test annotation.
Recognition rate = correctly identified expected preference concepts / total expected preference concepts × 100%. For a scored recommendation turn, PASS requires ≥80% recognition, all verifiable hard constraints satisfied, and specific explanations connecting at least one documented attribute of each recommendation to the user’s preferences. A valid no-match response passes the constraint requirement when no eligible hotels exist; the evaluator must verify the no-match condition.
FAIL if recognition is below 80%, a verifiable hard constraint is violated, or explanations are generic, misleading, or not tied to supported attributes. If no preference concepts exist, record recognition as N/A and judge whether the agent appropriately requests enough information; do not divide by zero.
4. C — Intent understanding and ambiguity handling (1 point)
A prompt has material ambiguity only when multiple plausible interpretations would substantially change retrieval, ranking, or constraint application. Vague wording alone does not always require clarification. A safe broad recommendation may be acceptable if the request explicitly invites open-ended suggestions and the agent does not invent hard constraints.
Clear intent: PASS if the agent proceeds without unnecessary clarification.
Materially ambiguous or essential missing information: PASS if it asks a targeted question or offers concise, meaningful interpretation options before making definitive recommendations.
Multi-turn case: PASS only if the subsequent recommendation incorporates the user’s clarification.
FAIL if the agent silently chooses a material interpretation, imposes an invented numerical budget, asks irrelevant questions, or ignores the follow-up.
Example: “I want somewhere I can just switch off.” Appropriate clarification could distinguish a secluded retreat, beachfront relaxation, and a wellness-focused hotel. These are possibilities to confirm, not assumed user requirements.

For comparable case-level scores, evaluate a clarification case only after the predefined follow-up has been supplied. Then assign A, B, and C (maximum 3). If the interaction ends at the clarification question, report an interim score with B = N/A and do not compare its total with completed cases. Do not award full case-level scores for an unfinished interaction.
6. Response time (separate operational metric)
Clarification turn: target ≤45 seconds from submission to complete clarification response. Record pass/fail latency compliance separately.
Clear request: lower end-to-end latency is preferred; no arbitrary hard cutoff.
Record total latency and, where instrumented, preference extraction, filtering, retrieval, ranking, and generation latency.
Report median, mean, and p95 latency; report clarification compliance as fraction of clarification turns completed within 45 seconds.
7. Test design and annotation
Create a mix of clear, multi-constraint, vague, indirect, conflicting, missing-location, no-match, unsupported-availability, and multi-turn scenarios. Freeze expected concepts and follow-up answers before running the model. Use only dataset-supported attributes for relevance labels. Include both easy and difficult cases; reserve a held-out test set for final evaluation.

8. Evaluation protocol
1. Freeze the dataset version, agent version, model settings, and prompt/test annotations.
2. Run each test through the same pipeline; log extracted preferences, candidate IDs, similarity scores, final IDs, answer, and timings.
3. Verify factual claims against exact hotel rows.
4. Compare extracted preferences with pre-annotated concepts; check hard constraints and explanations.
5. Judge clarification handling using the material-ambiguity annotation and the follow-up turn when needed.
6. Assign binary A/B/C scores with evidence; mark N/A only for interim turns.
7. Calculate average score out of 3, normalized score, criterion pass rates, perfect-case rate, and latency statistics on completed cases.
8. Optimize on development cases; report final results on an untouched held-out set.
9. Scoring formulas
For completed cases, case score = A + B + C (0–3). Average score = sum(case scores) / number of completed cases. Normalized score (%) = sum(case scores) / (3 × number of completed cases) × 100. Criterion pass rate (%) = number of completed cases scoring 1 on that criterion / number of completed cases × 100. Perfect-case rate (%) = completed cases scoring 3/3 / number of completed cases × 100. Do not mix interim N/A cases into these denominators.

11. Optimization and interpretation
Factual failures point to grounding, citation-to-row verification, or generation controls. Relevance failures point to preference extraction, hard filtering, embedding text, or ranking. Intent failures point to ambiguity detection and dialogue policy. Latency failures point to unnecessary calls or expensive steps. Change one major component at a time and preserve a baseline for comparison.
This rubric is an evaluation specification, not a supervised training dataset. To fine-tune a model, separate labeled examples and a training procedure would be required. It can immediately guide automated tests, prompt changes, retrieval/ranking development, and regression checks.
